### 4-2. 파생 오류 — 계산에 실제로 쓰인 곳이 있다

> **[G-d] 6원 차이는 산식이 아니라 규약의 문제다 — Codex 지적을 절반만 수용한다.**

>

>
> **[G-d] 확정 — 원장 full precision, 조정 EPS 105,318원.** Codex 최종 승인(2026-08-07). 세율이 파생값이므로 표시 라벨(23.46%)은 반올림 표기이고 계산에는 원장 나눗셈 결과를 쓴다. **6원 차이 자체는 무의미하며, 진짜 결함은 규약이 문서에 없었다는 것이다** — §11에 규약을 명시해 재발을 막는다.
>

**단, 이 라인의 원래 취지("어느 쪽이 맞는지 지금 결정하지 말 것")는 절반만 해소됐다.**

## 6. P0-5 [필수] corp-action 레지스터

### 6-1. 문제

프로파일의 주식수가 **하드코딩**이다(`705,656,476` = 2026Q1 기준). 한 분기 사이에:

```
자기주식 소각  −15,300,000주  (2026-01 이사회 결의·집행)
ADR 국내 신주  +17,790,000주  (2026-07-14 납입 · 07-29 국내 추가상장)
⇒ 상장주식수 728,002,365 → 730,492,365   유통 701,691,520 → 719,481,520
```

수동으로 못 잡으면 **EPS 전 계열이 조용히 틀린다.** 2026Q3 롤에서 즉시 문제가 된다.

### 6-2. 설계 — **명시적 주식 상태 delta** (rev.2, Codex 재설계 요구 수용)

rev.1의 `shares_delta` + `affects` 조합은 소각·신주·우선주·분할을 **모호하게 만든다**. BVT 스키마(`schemas/models.py` `CompanyProfile`)의 실제 상태 변수에 1:1 대응시킨다.

**스키마 상태 변수 (확인 완료)**

```
shares_total        보통주 + 우선주 총발행
shares_ordinary     발행 보통주
shares_preferred    발행 우선주
treasury_shares     자기주식 (보통주 기준)
shares_outstanding  @property = shares_ordinary − treasury_shares   ← per-share 분모
```

**corp-action 레코드**

| 필드 | 타입 | 설명 |
|---|---|---|
| `effective_date` | date | 효력 발생일 (소각일 / 신주 납입일) |
| `kind` | enum | `treasury_cancellation` \| `new_issue` \| `buyback` \| `split` \| `reverse_split` |
| `ordinary_issued_delta` | int | 발행 보통주 증감 (부호 있음) |
| `preferred_issued_delta` | int | 발행 우선주 증감 (부호 있음) |
| `treasury_delta` | int | 자기주식 증감 (부호 있음) |
| `split_ratio` | float \| null | 분할·병합 전용. **delta로 표현하지 않는다** — `kind ∈ {split, reverse_split}`일 때만 non-null이고, 이때 세 delta는 모두 0이어야 한다 |
| `source` | str | 공시 문서 ID |
| `confidence` | enum | `confirmed` \| `derived` |

**SK하이닉스 2026 적용 예**

| 일자 | kind | ordinary_issued_delta | treasury_delta | confidence |
|---|---|---:|---:|---|
| 2026-01 | `treasury_cancellation` | **−15,300,000** | **−15,300,000** | `derived` (회사 발표 "약 1,500만주" + 상장주식수 역산) |
| 2026-07-14 | `new_issue` | **+17,790,000** | 0 | `confirmed` (ADR 공모 납입) |

*소각은 발행주식과 자기주식을 **동시에** 줄이므로 두 delta가 모두 음수다. rev.1의 `affects: both`로는 두 값이 같은지 다른지 표현할 수 없었다.*

### 6-3. 게이트 — **3값 각각 검증 + 분모 최종 확인**

`shares_total` 하나만 비교하는 것으로는 부족하다(우선주·자기주식 오차가 상쇄돼 통과할 수 있다).

| # | 검증 대상 | 기대 (2026Q2 롤) |
|---|---|---:|
| 1 | `shares_total` | 730,492,365 |
| 2 | `shares_ordinary` | 730,492,365 (우선주 0) |
| 3 | `treasury_shares` | 11,010,845 |
| 4 | **`shares_outstanding` (분모 최종 확인)** | **719,481,520** |

- 1~4 중 **하나라도** 레지스터 산출값과 다르면 **block**
- `confidence=derived` 항목이 분모에 기여하면 **warn** → 리포트에 "추정 분모" 표기 강제
- 분할·병합 레코드는 delta 경로가 아니라 `split_ratio` 경로로 적용되는지 별도 테스트
- 테스트: 2026Q1 → 2026Q2 롤에서 위 4값이 자동 산출되는지

## 11. [신설] 수치 정밀도 규약

§4-2의 6원 차이가 드러낸 것은 계산 오류가 아니라 **규약 부재**다. 파생값이 늘어날수록 반복된다.

### 11-1. 규칙

| # | 규칙 |
|---|---|
| R-1 | **원장값(공시 원 단위)은 절대 반올림하지 않는다.** 반올림은 최종 출력 1회 |
| R-2 | **파생 비율(세율·마진·증감률)은 full precision으로 계산하고, 표시 라벨만 반올림한다.** 라벨을 계산에 되먹이지 않는다 |
| R-3 | 문서에 파생 비율을 적을 때는 **라벨과 계산값을 함께** 남긴다 — 예: `유효세율 23.46% (= 28,785.8 / 122,708.4)` |
| R-4 | **정의상 정확한 값**(앵커 16.4%, 가정 확률 40% 등)은 표시값이 곧 계산값이다. R-2 대상이 아니며, 문서에 그 사실을 표기 |
| R-5 | 서로 다른 계산 경로(손계산 vs 엔진)의 값을 한 표에 넣을 때는 **경로를 라벨링**하고 차이를 명시한다 (rev.1의 "전 항목 diff 0" 과장이 여기서 나왔다) |

### 11-2. 적용 예 — 본 건

```
유효세율  라벨 23.46%   계산값 0.2345870372  (= 28,785.8 / 122,708.4)   ← R-2, R-3
앵커 세율  16.4%        계산값 0.164          (정의상 정확)             ← R-4
조정 EPS  70,608 + 45,348 × (1 − 0.2345870372) = 105,317.947 → 105,318  ← R-1
```

### 11-3. 검증

`score_*.py`·리포트 생성기가 파생 비율을 출력할 때 **라벨과 원장 산식을 함께** 내보내도록 한다. 문서에 라벨만 있고 산식이 없으면 재계산 시 이번과 같은 불일치가 재발한다.
